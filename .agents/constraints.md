# Shared AI Constraints

This file is the human-maintained source of truth for assistant behavior in this repository.
Framework reference lives in the `AI.md` of each module and extension; it is never copied into this repository.

## Workflow

- Use putnami or ./putnamiw for build, test, lint, serve, install, and upgrade workflows. Do not use npm, yarn, pnpm, bun, go, or python directly for normal workspace verification unless the task explicitly requires it.
- After adding or removing extensions, run putnami extensions install and putnami context generate.
- Use putnami deps add/remove for dependency changes. Do not run bun add, npm install, or other package-manager commands directly.
- The verification gate is `putnami lint,test,build,validate <selection> --enforce-coverage` — the exact command CI runs. `validate` plans `validate-workspace` with it, so the gate never names it. `putnami.ci.json` (version 3) declares those commands, the rules that name the channels a branch publishes, and the environments that follow them; Putnami Cloud's native runner reads it. Keep the file's `commands` in sync with this line.
- Discover code through the CLI, then grep. `putnami projects list|describe|owner|deps|why` answers which projects exist, what describes one, who owns a path, what it depends on, and whether a change to one impacts another; `putnami context map|pack` orients on the workspace or on a project; `putnami <verb> --impacted --dry-run` lists what a change affects. Use grep or rg for literal string and symbol lookups. The verification gate stays on the CLI (see the gate rule above).
- Two identifiers name this workspace in Putnami Intelligence and are not interchangeable: the workspace UUID `a3839d53-5b31-48d4-8924-fb29df25c743` addresses the control plane (`/v1/workspaces/<uuid>/…`, `POST /v1/intelligence/index`); the graph slug `dev`, pinned in `putnami.workspace.json` under `options."@putnami/cloud".intelligence`, routes queries (`?workspace=dev`). Either one in the other's place fails closed with "Intelligence is not enabled for this workspace" or a 403. `PUTNAMI_INTELLIGENCE_URL`, `PUTNAMI_INTELLIGENCE_WORKSPACE` and `PUTNAMI_INTELLIGENCE_AUDIENCE` override the manifest for one process.

## Implementation planning and local proof

- These obligations apply to ordinary implementation requests whether or not the user names a workflow or skill. Inspection, discussion, and planning-only requests remain read-only; these rules do not by themselves authorize implementation, issue creation, pushes, pull requests, deployment, or merges. An authorized `build` run publishes its own pull request (see below).
- Before editing, reuse any current valid plan and make the remaining planning proportionate to the change. Identify the smallest useful executable vertical, existing mechanisms to reuse, known gaps, acceptance behavior, dependencies, the local environment it needs, and the command or harness that will prove it. A change that reaches a service needs an early running baseline or walking skeleton; a library- or docs-only change keeps a proportionate proof. Planning-only requests stop after the plan; when planning is a phase of an authorized implementation, continue without requesting a second approval.
- Qualify each claimed complete vertical from the actual branch or worktree. A changed project reaches a workload when it is one or when a workload's `runsWith` closure includes it; run `putnami qualify <project> --target local` for each reachable workload. The command composes the workload with the workloads it runs with, production-mode, with per-run databases and real migrations, waits on the typed ready event, sends the derived read-only smoke beyond health, and tears everything down. Read its verdict (`--output=json`, the result's `data`): `state` is `passed` or the proof failed; `binding` (`kind: tree`, `fingerprint`, `dirty`, `headSHA`) names the tree it proved; `cleanup.state` is `clean`, or the run left resources behind. A TypeScript workload without a committed route inventory needs `putnami build --projects <id>` first, otherwise the verdict is `unsupported`. Internal providers and consumers stay real; use doubles only at genuine external boundaries and disclose them. Generated-client work must also exercise provider declaration → generation → compiled or loaded emitted client → real bound consumer call.
- Reuse Putnami selection, manifests, dependency graph, lifecycle cleanup, sessions, and existing test or component harnesses. The verdict's `binding.fingerprint` is the same digest as a gate session's `tree.fingerprint`: the proof and the gate cover the same tree only when the two are equal, and `HEAD` plus dirty path names alone does not identify uncommitted code. Rerun affected proof after relevant changes. Local execution proof for a reachable workload is `putnami qualify <project> --target local`; its verdict is the evidence. Do not hand-author a receipt, a per-workload supervisor, or a second orchestration architecture. A library-only or docs-only change reports `NOT APPLICABLE` with the reason.
- The ordinary `lint,test,build,validate` gate and local execution proof are separate evidence. A ready-for-review or completion report states both — the gate session and, for local proof, the verdict's `state`, `binding`, and `cleanup` — or explicitly says why local proof is not applicable, missing, or blocked. A checkpoint commit, push, or draft PR is durable backup, not completion; skipped, absent, impossible, timed-out, zero-scenario, or stale proof is never reported as success.
- Prefer one integration branch and one draft-to-ready pull request with meaningful commits for a coherent feature. Use parallel workers or separate/stacked PRs only where ownership and contracts are genuinely independent and isolation is safe. Integrate serially on a coordinator-owned checkout, requalify affected interactions on the combined branch, and prioritize integration failures before opening more scope. Do not globally enable concurrent Putnami jobs without proven tool isolation.

## Repository Layout

The repo is organized by ownership — each language ecosystem is self-contained. Full rules live in CONTRIBUTING.md (Repository Layout); the short map:

- `tooling/` — workspace-wide machinery: the CLI (`tooling/cli`, Go), extension SDK, scaffold, client generator, SDD extension, agent workflows, hooks, and tooling samples.
- `intelligence/` — public Intelligence code: the area detector (`intelligence/areas`).
- `cloud/` — public client code of the hosted platform, such as the Cloud runtime destination libraries.
- `protocols/` — cross-pillar wire contracts (JSON schemas + fixture corpora) shared by frameworks, tooling, and platform. Structured CLI output, workspace/project config, extension manifests, features, support status, and the other contracts are defined here.
- `typescript/`, `go/`, `python/` — each language root follows the same shape: `extension/` (owns the generic lifecycle jobs: build, test, lint, serve, package), `framework/` (runtime APIs — Go modules publish as `go.putnami.dev/*`), `templates/`, `samples/`. Framework packages must not compete with the language extension for generic lifecycle command names; extension identity is manifest- and package-driven, not path-driven.
- `sites/` — deployed sites: `sites/putnami.dev` (documentation) and `sites/telemetry.putnami.dev` (CLI-usage receiver).

Docs live next to the thing they describe, in each package's `doc/` folder; `sites/putnami.dev` publishes those folders but does not own their content. Most framework modules also ship an `AI.md` API reference (`go/framework/*/AI.md`, `typescript/framework/*/AI.md`).

## Code Style and Testing

- Formatter/linter is Biome (`biome.json`), not ESLint or Prettier; `biome.json` sets 2-space indentation.
- TypeScript tests use `bun:test`, files named `*.test.ts` or `*.spec.ts` in `test/` directories. Go tests use stdlib `testing`, colocated `*_test.go`. Python tests use pytest under `tests/`.
- The workspace pins Bun via `packageManager` in `package.json`. `./putnamiw` is the committed wrapper for fresh clones: it builds the CLI from source, resolving a Go toolchain itself, so no account, credentials, or globally installed tools are required to build, test, or lint this repository. `--download` serves consumer workspaces; here it is refused (see the next rule).
- **This repository is the source of its own CLI, so `./putnamiw` is the only supported entrypoint here.** The root `putnami.lock.json` records `"cli": { "source": "workspace" }`, not a published pin; a globally installed `putnami` (or a runner's baked one) is refused with a hard error naming `./putnamiw`. `PUTNAMI_NO_RELAUNCH=1` does not bypass that — it is the escape from a broken published pin, and there is none here. `./putnamiw` keys its build on the content of `go.work go.work.sum tooling protocols go`, so an edit under `protocols/` or `tooling/extension-sdk` rebuilds without `--bootstrap`. See `tooling/cli/doc/adr/0028-self-hosted-cli-source-workspace.md`.
- **Every extension whose source lives here loads from that source, never from a published build.** `putnami.workspace.json` lists `/cloud/extension`, not `@putnami/cloud`: a pinned build carries the protocols of its own commit, so a protocol change merged here would pass its pull request and then fail `publish` on `main` against the older validator. A hosted run (`--credential-fd`) keeps the provider capabilities of `/cloud/extension` (cache, release sets, registry credentials, reporters) because `./putnamiw --print-engine` runs `putnami extensions prepare`, which prepares its runtime from the tested tree before the run; the run loads that runtime from the artifact store and prepares none itself. Only `@putnami/intelligence`, built in another repository, is loaded by name. See `tooling/cli/doc/adr/0055-run-credentials-stay-out-of-repository-processes.md`.

## Agent Workflows

- The workflow source lives in `tooling/contributor/src`, the agent content of the `@putnami/contributor` extension: canonical `build`, `spec`, `design`, `review` and `check`, plus the active explicit-only `content-bump` integration and their workers. The former `plan`, `execute`, `fix`, `epic`, `code-review`, `adr`, `prototype`, four `putnami-*` aliases and `fix-loop` entries, and the `fix-light` and `epic-analyst` workers, are removed by an explicit breaking change. Build owns the single shared loop; neither natural-language planning nor a named task grants backlog selection, task claim, merge or deployment authority without the accepted mandate. A `build` run publishes its own pull request by default; `--local` keeps it local. The root declares the extension by path in `extensions` and opts into its content with `agentArtifacts: ["extension:@putnami/contributor"]`, the only way agent content is installed. The superseded `tooling/agent-workflows` and `tooling/maintainer-workflows` projects are deleted. A clone that still records them after a pull deletes the ownership records every agent-content command names, then runs `./putnamiw install`, which drops their old lock pins.
- `.agents/skills/`, `.claude/skills/`, `.claude/agents/` and `.codex/agents/` are generated from that source. Never hand-edit them: edit the source, run `./putnamiw context generate`, and commit both. `TestLocalAgentContentMatchesCommittedRoot` fails the moment the committed copies differ from what the source builds.
- The workflows reach issues and pull requests only through `putnami tasks|proposals <operation>`, bound to `@putnami/github-collaboration` in `options.collaboration` of `putnami.workspace.json`; memory is unbound here. This repository's contributor conventions (labels, states, workflow profiles, the English rule, publication defaults, the content-bump integration) live in `options["@putnami/contributor"]` of the same file. Change a convention there, not in the skills.
- `audit` (`.agents/skills/audit/`, `.claude/skills/audit/`) and its workers (`.claude/agents/prune-*.md`, `.codex/agents/prune-*.toml`) are the agent content of the published `@putnami/intelligence` extension, which the root opts into with `extension:@putnami/intelligence` and `./putnamiw install` materializes. Never hand-edit them. This repository's audit rubric is `.agents/audit/profile.md` and its own deterministic checks are `.agents/audit/checks.sh`; `options["@putnami/intelligence"].audit` names both and sets the group priority order. `.codex/config.toml` and `.claude/settings*.json` are host policy, not workflow content, and stay hand-authored, except the hook handlers an opted-in extension declares (see Generated Assistant Files).
- Model tiers are equivalent across hosts: Fable 5.1 ↔ exact `gpt-6-astra`, Opus 5.5 ↔ exact `gpt-6-sol`, Sonnet 5 ↔ exact `gpt-6-luna`. A worker runs on the same tier on both hosts; tiering may change worker instructions and reasoning effort, but never picks a model outside these three. Orchestration and review stay on Astra. `reviewer` and `prune-triage` run on Astra, `fix-heavy` and `fix-standard` on Sol, `prune-apply` on Luna.
- A `build` run follows its actual mandate through the required stage. By default it ends with its pull request ready for review: `./putnamiw change finalize` and its exact proposal receipt, in the same run as the final gate. A `--local` run ends with local evidence. Use `./putnamiw tree fingerprint` for tree identity and bind it to the producer session; no shell fingerprint wrapper is installed. A passing subtask or clean local gate alone does not complete a broader outcome.

## Generated Assistant Files

- The `putnami:guidance v2` block inside `CLAUDE.md` and `AGENTS.md` is generated by `putnami context generate`. Never hand-edit the block: `TestGeneratedGuidanceMatchesRepositoryCIDocument` in `tooling/cli/internal/commands/agentctx/gate_command_test.go` runs inside `putnami test` and fails the moment the committed bytes differ from what the generator produces for this workspace (the gate is the blocking commands of the root `putnami.ci.json`). To change the block, edit `guidanceBlockTemplate` in `tooling/cli/internal/commands/agentctx/agent_md.go`, run `./putnamiw context generate`, and commit the result. Every byte outside the block belongs to this repository.
- Besides the block, Putnami writes one thing into a workspace root: the host hooks an extension declares, into `.claude/settings.json` and `.codex/hooks.json`. `init`, `install` and `upgrade` write them when the workspace opts into the extension's agent content and binds the collaboration contract the hooks need. They replace their own handlers, keep every other entry, and remove their handlers when the opt-in or the binding goes away (`tooling/cli/doc/adr/0081-the-core-writes-declared-host-hooks.md`). No other command writes a hook file. Putnami serves no MCP server and writes no `.mcp.json`: an explicit `install` or `upgrade` removes the `putnami` entry an earlier release wrote there, when it is exactly the one Putnami wrote, and keeps a changed one with a warning (`tooling/cli/doc/adr/0082-putnami-serves-no-mcp-server.md`). Putnami never writes this file (`tooling/cli/doc/adr/0055-repository-rules-live-in-agents-constraints.md`).
- Prefer the real templates under `<lang>/templates/` and the module `AI.md` files over any prose recipe.

## Python experimental surface

- `@putnami/python`, `python-server`, and `python-library` are experimental,
  explicit opt-in, non-default, and unsupported for Go or TypeScript parity.
- The Python surface is the extension and its templates only; no Putnami Python
  framework package family ships today. Do not infer feature, compatibility, or
  production parity from the generated context's generic Python examples.
- Keep Python features at `modeled` until a build or test producer emits exact
  Feature Evidence. Never write evidence by hand to promote them.

## Repository Conventions

- Put persistent project-specific instructions in this file. Nothing regenerates it.
- Keep product-code changes inside the owning domain (tooling/, intelligence/, cloud/, protocols/, go/, typescript/, python/, sites/). Agent guidance and host configuration belong in the established .agents/, .claude/, and .codex/ roots.
- Do not add tracked files under retired roots such as apps/, core/, extensions/, framework/, packages/, web/, samples/, scripts/, or docs/.
- For user-facing changes, update adjacent docs in the same owning domain, in the same PR.
- A change that adds or alters user-visible behavior also carries its product intent: a feature declaration in the owning project's `putnami.features.json`, one spec under `specs/`, and — when the change rests on a durable choice — a decision record under `<project>/doc/adr/`. Never hand-write feature evidence; build and test producers emit it.
- Every project carries a feature of its own, a spec, or a reviewed `featureAuthority` in its `putnami.json` (D-025). `validate` fails a project that carries none unless `options.sdd.featureCoverage.debt` in `putnami.workspace.json` names it. Never add an entry to pass the gate: the pull request that gives a listed project its answer removes its entry. A protocol owns the feature of its contract, and each implementation proves its requirements in its own tests, under a check of its own (D-026).
- A public support status is a separate, reviewed decision recorded only in `putnami.support.json` (rules in `protocols/support`). Do not claim one in prose, and do not add an entry without that review.
- A domain is a top-level scope: a root directory whose `putnami.json` is a scope manifest (`tooling/`, `intelligence/`, `cloud/`, `protocols/`, `go/`, `typescript/`, `python/`, `sites/`). Its projects are that scope's `includes`.
- Write every GitHub artifact (issue, pull request, comment, commit message) and every code comment and doc in English, whatever the language of the conversation. The only exceptions are UTF-8 test fixtures and proper nouns such as RGPD or CNIL. `./putnamiw change language text|files|commits|tasks` is the shared detector: `change finalize` refuses a non-English PR, `/check` runs it on the branch, and `/audit` files the remaining debt under `prop/language`. The active audit integration keeps `check/scripts/english-only.sh` only as a thin relay to that native command.
- A code comment states the contract of the code next to it, never its history. Do not write why a guard exists, which incident motivated it, which issue or PR introduced it, or what would break without it: state the rule in the present tense, or say nothing. A lint escape (`//nolint`, `as any`, `@ts-ignore`, `biome-ignore`) is a change to the code or to the lint rule, not a comment to justify; `/audit --prune` removes both classes.
- Use Conventional Commit style for both commit messages and PR titles: `type(scope): summary` when a useful scope exists, otherwise `type: summary`.
- Pick the type from what the diff changes, never from the workflow that produced it, the task label, or the word "fix" in a finding. Ask in this order and take the first yes:
  - `test` — every changed path is a test, a fixture or test data, including a flaky test made deterministic. Native `change finalize` refuses `fix` and `feat` here.
  - `perf` — the point is less time, CPU, memory, I/O or allocations, behavior unchanged: a faster gate, a cache hit, a smaller archive.
  - `docs` — only documentation or code comments.
  - `ci` — only `.github/` workflows or CI runner configuration.
  - `build` — dependencies, `go.mod`, lockfiles, toolchain pins, or packaging, with no product code change.
  - `refactor` — product code restructured, behavior unchanged, including dead-code removal that no caller observes.
  - `style` — formatting only.
  - `fix` — observable behavior was wrong and is now right.
  - `feat` — new observable behavior.
  - `chore` — upkeep with none of the effects above: a content-lock bump, a regenerated artifact.
- Do not prefix commit messages or PR titles with assistant/tool markers such as `[codex]`, `[claude]`, or similar automation labels.
- No commit, PR title, PR body, comment, code or document names the agent, model, or version that produced it: no `Co-Authored-By:` agent trailer, no "Generated with" line, no session link, no model name in a commit body. Turn off host attribution (`.claude/settings.json` sets `commit` and `pr` empty and `sessionUrl` false). A pull request opened by an agent host's own button or app writes its own footer, which no repository setting turns off: open an authorized pull request from the session with `./putnamiw change finalize` instead. Record which models worked on a mission in the mission memory checkpoint, outside this repository. Native finalization refuses a commit, title or body that names an agent, and the `agent-attribution` step of `validate` fails a squash message that names one (`options.sdd.agentAttribution` is `"forbid"`).
- `main` takes one squash commit per PR. GitHub uses the PR title as its title and the PR body as its message, the merge button included. Branch commits are checkpoints and never reach `main`, so their messages matter less than the PR's.
- The PR title is the squash commit title: a Conventional Commit, per the rules above.
- The PR body is the squash commit message. Write the net change of the whole branch in a few plain paragraphs, the way a good commit body reads: what changes, why, and what it deletes (D-002). No headings, no file lists, no test output, no checklists, no proof. Native `change finalize` refuses a heading and a body over `publication.bodyMaxBytes` (1500 bytes), and joins the lines of each paragraph: GitHub wraps the squash message at 72 columns, so an author-wrapped body reaches `main` with broken lines.
- Rewrite the PR body whenever a push changes the branch's scope, before asking for review. A body that describes an earlier state of the branch is a review finding.
- Verification evidence (files changed, the gate, the local proof) goes in a PR comment. Native `change finalize` posts it when it marks the PR ready.
- Open the PR as a draft as soon as the work has a plan, with `./putnamiw change finalize --draft`: it commits an empty checkpoint when nothing is committed yet, and the squash drops it. When the change touches a declaration (`putnami.features.json`, `specs/*.json`, `specs.baseline.json`, `putnami.architecture.json`, `decisions.json`, an ADR), commit those files alone and push them before any code, then read and answer the reviewers' comments on them at each later checkpoint. At each milestone whose `--projects` gate passes, commit and push with `--draft` too. Mark it ready for review with `./putnamiw change finalize --verification-file <dossier.json>` once the final local gate passes. Putnami CI holds runs on a draft; start one by hand with `./putnamiw cloud ci start --pr <n> --sha <sha> --reason <why>` when you need hosted feedback early.
- Before the final gate, measure the machine with `./putnamiw doctor --machine`. Above 0.70, run no local impacted gate: use `./putnamiw change finalize --gate ci --workflow-file <immutable-workflow.json>` when naming a parent task, which marks the PR ready, starts Putnami CI, and waits for its check on the pushed commit. A failing check returns the PR to draft. Otherwise build runs the one final impacted gate and passes its current dossier to `change finalize --verification-file`; native finalization never runs or retries a local gate.
- Ask the user before recording DX feedback or filing issues about tooling pain.
