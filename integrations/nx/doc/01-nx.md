# Run a Nx repository with Putnami

`@putnami/nx` turns each project of a Nx workspace into a Putnami project,
with an edge to each project Nx says it depends on. Putnami selects what a
change affects and gives the verdict. The mode decides who runs the targets
and who caches them.

| Mode | Build, test and lint | Cache |
|---|---|---|
| `import` | A TypeScript project's targets whose script already runs `bun build`, `bun test` or `biome` run as `@putnami/typescript` tasks; every other target runs `nx run` | Putnami's, for the imported tasks; Nx's for the rest |
| `delegate` | Every target runs `nx run <project>:<target>` | Nx's, local or Nx Cloud; Putnami caches nothing |

## Adopt it

`@putnami/nx` is not published yet: until its first release, `putnami init
--from nx` stops at the extension install, after it has written the workspace
files, and a workspace loads the extension from a source checkout.

At the root of the repository, where `nx.json` lies:

```bash
putnami init --from nx
```

In a terminal, `init` asks for the mode, with `import` preselected. Without a
terminal, in CI or from an agent, it imports. `--mode import` or
`--mode delegate` skips the question:

```bash
putnami init --from nx --mode delegate
```

`init` writes a workspace that declares `@putnami/nx`, and `@putnami/typescript`
in import mode, records the mode in `options["@putnami/nx"].mode`, installs
the extensions and runs `putnami projects sync`.

The projects come from the graph export `graph.json` at the root
(`nx graph --file=graph.json`) when the repository has one, else from
`nx.json`, each `project.json` and each workspace `package.json`. The sync
does not run Nx.

## Rerun it

Rerun `putnami init --from nx` in the workspace it wrote to see what a sync
would change, such as after switching mode: it prints the diff of each
`putnami.json` and the mode change, and writes nothing. The preview reads
`@putnami/typescript` as declared when `--apply` would declare it, so a switch
to import mode previews the targets that move to it. `--apply` records the
mode and synchronizes:

```bash
putnami init --from nx --mode delegate --apply
```

## What the sync writes

`putnami projects sync` runs the extension's sync task, in the mode the
workspace records. It writes in each project's `putnami.json`:

| Member | Value |
|---|---|
| `extensions` | `@putnami/nx`, and `@putnami/typescript` for an imported TypeScript project, beside any other extension the file names: a `putnami.json` that names extensions is claimed by those alone |
| `dependencies` | The project ID of each Nx project it depends on, such as `/packages/pricing`; a dependency on a project that is no Nx project is kept |
| `disable.jobs` | `build`, `test` or `lint` when the project has no such target; in import mode `@putnami/nx:<task>` for a target `@putnami/typescript` runs, and `@putnami/typescript:<task>` for one that keeps running through Nx. The sync owns these entries: one written by hand is replaced at the next sync |
| `options.@putnami/nx.tasks.test.reports` | The JUnit and Cobertura or LCOV files the project's jest or vitest configuration names, relative to the project |

It keeps every other member, and rewrites a file only when a member it owns
changes, with two-space indentation and sorted keys. A project that left the
graph loses the extension and what the sync owns.

The sync lists, with the reason, each target it maps to no Putnami task:

- a target other than `build`, `test` and `lint`, such as `serve` or `e2e`,
  which still runs with `nx run <project>:<target>`;
- in import mode, a `build`, `test` or `lint` target of a project that is not
  TypeScript, or that runs something other than what `@putnami/typescript`
  runs, which keeps running through Nx;
- a delegated `test` whose configuration names no report: its result is the
  exit code alone.

### Import mode

A project is TypeScript when it holds `package.json` and a `tsconfig*.json`
or a `.ts` source. `@putnami/typescript` takes over a target only when the
target's script, or `nx:run-commands` command, already runs what its task
runs, so no target changes the tool that checks it:

| Task | `@putnami/typescript` runs | Script or command it takes over |
|---|---|---|
| `build` | `bun build` | `bun build …` |
| `test` | `bun test` | `bun test …` |
| `lint` | Biome | `biome …` |

A `jest`, `vitest`, `eslint` or `tsc` target, and every target an Nx
executor runs, such as `@nx/jest:jest` or `@nx/webpack:webpack`, keeps
running through Nx, and the sync lists it. One extension runs each task, so
no Putnami cache sits over Nx's.

### Import some projects of a delegated workspace

In delegate mode, `options["@putnami/nx"].import` lists project paths and
globs, such as `/packages/pricing` or `/packages/*`: a leading `/` is
ignored, and `*`, `?` and `[...]` match within one path segment. The sync
writes each project an entry selects as import mode writes it, and every
other project as delegate mode writes it. Import mode reads no list.

```bash
putnami init --from nx --import /packages/pricing --apply
```

adds the entry, declares `@putnami/typescript`, and synchronizes; without
`--apply` it previews. An entry that selects no project is reported as
`nx.import_unmatched`. The sync job's `import` parameter outranks the option,
as `mode` does, so a preview reads the list it would record.

## What a task runs

Each delegated task first compares `npx --no nx --version` with the `nx`
version the root `package.json` states in `devDependencies` or
`dependencies`, then runs at the workspace root:

```bash
npx --no nx run <project>:<target> --outputStyle=static
```

`npx --no` runs the repository's own Nx and never downloads one. Nx's
`dependsOn` runs the upstream targets, and Nx's cache answers them. Each task
depends only on its project's graph step, which runs nothing: a change runs
Nx on its project and the projects that depend on it. Putnami's cache is off
for every task, and the result records `delegatedTo: nx`.

The test task removes the reports the sync names before its run, then reads
them into the test and coverage summary. A path that names `<rootDir>` is
read from the project; under `@nx/jest`, jest-junit writes its
`outputDirectory` from the workspace root.

## Keep the graph current

Nx infers edges from imports, so an import can change the graph with no
change to a manifest. `putnami validate` compares each project's
`putnami.json` with what a sync would write, and fails with `nx.sync_stale`
when one would change. Run `putnami projects sync` and commit the result.
