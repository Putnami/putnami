# ADR 0004 — A declared output may police its own drift

- **Status**: accepted
- **Scope**: `go.putnami.dev/protocol/extension` (`protocols/extension`), the
  `drift` member of a declared output, and the CLI's declared capture and
  restore paths

## Context

Some declared outputs are bytes the repository commits: a generated client, a
schema sidecar, a rendered document. The question that matters is whether the
committed bytes still equal what the current inputs generate. Only the writer
can answer, and only at the moment it writes: anything later in the session
reads a tree the generator, or a cache restore of its entry, already
rewrote. An extension that re-derives the answer must rebuild and re-render
everything in a nested session, which costs seconds on every `validate`.

## Decision

1. **Drift detection is a property of a declared output.** A declared output
   may carry `drift: "warn" | "fail"`. The engine snapshots the output path
   immediately before the task writes it, compares it with the bytes present
   afterwards, and reports a difference as one diagnostic,
   `generated-output-drift`, listing added, removed and changed paths
   (sorted, bounded, workspace-relative). Under `fail` the task fails with
   that code, and its outputs are still written or restored, so the worktree
   holds the regenerated bytes to commit. Under `warn` the task keeps its
   status. No extension re-implements the comparison.
2. **The reference is taken immediately before the task, on both paths**:
   before the process starts when the task executes, before the recorded tree
   is swapped in when it is restored. A cold and a warm run reach one verdict.
   For a literal `path` the reference is that path. For a `pathFrom` output it
   is a digest of the project tree (dot-directories, `node_modules` and
   `vendor` skipped), so `pathFrom` carries the policy under the `project`
   root only.
3. **Neither the reference nor the verdict is a cache-key input.** They are
   facts about the worktree, not the task's inputs. A drift failure is never
   recorded as a replayable failure, and the task's successful entry is still
   published: the next run hits it and judges the worktree again, which is how
   a fresh CI checkout of stale committed bytes fails from the restore path.
4. **The field is part of the task contract.** It enters the task-contract
   digest, so declaring it moves the task's cache key once.
5. **The field enters under CLI contract 4**, for the reason in
   [ADR 0002](0002-runtime-toolchains-are-lock-pinned-under-the-current-contract.md)
   decision 7.

Invariants:

- The policy rides only on a durable, non-sensitive `file` or `directory`
  output under the `project` or `workspace` root. The `command-output` root,
  a runtime file and an invocation-scoped output have no committed state to
  drift from. Each rule is a validation error.
- Both snapshots apply the same walk rule.
- A ceded subpath ([ADR 0003](0003-a-declared-directory-output-may-cede-one-subpath.md))
  and a preserved path
  ([ADR 0005](0005-a-declared-directory-output-may-preserve-workspace-files.md))
  are compared on neither side.
- An `optionalEmpty` output the run did not produce, or a restore of an entry
  recorded empty, leaves the path alone and is never drift.

## Rejected alternatives

- **Hand the writer a pre-session byte copy.** A per-run path in a cacheable
  task's environment is a per-run cache key. The digest reference stays on
  the engine's side of the task boundary.
- **Require a literal `path`.** Generated clients, which need the policy most,
  sit in a directory the project's configuration chooses.
- **A whole-workspace reference for `pathFrom` under the `workspace` root.**
  Unbounded cost before every such task, for no adopter.
- **Make the nested session cheaper** (re-entrancy guard, no remote cache
  provider). It keeps the nested session this decision removes.

## Consequences

- The policy must sit on the first writer of a path in a session, or that
  writer erases the evidence before the policed task compares. `clientgen-go`
  and `clientgen-ts` declare `fail` on their `client` output, and so do
  `@putnami/go` `build-describe` and `@putnami/typescript` `build-generate`,
  which write the same paths first.
- A provider excluded from `--impacted` (a `disable.tags` rule) has its drift
  judged only when it is selected explicitly.
