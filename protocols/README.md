# Putnami Protocols

`protocols` is a top-level concern of the repository: the standardization layer that keeps Putnami's three pillars — the **frameworks** (Go and TypeScript), the **tooling** (CLI, extension SDK, CI), and the **platform** (Putnami Cloud and other deploy targets) — agreeing on one set of wire shapes. Each package owns a single contract boundary, and its module name (`go.putnami.dev/protocol/<name>`) deliberately stands apart from any one consumer rather than belonging to the tooling that first defined it.

These packages are intentionally small and strict: each one defines a stable boundary that multiple languages and tools can read, validate, and test without depending on the rest of the system. The conformance matrix below is the live view of who implements or consumes each contract across those pillars.

| [`agentcontext`](./agentcontext/README.md) | Let MCP/intelligence tools orient in a project from framework-owned facts without rescanning the repo. | A deterministic, redaction-safe per-project agent-context document — identity/graph, composition roots, capability/contract/infra references, representative source ranges, tests, docs, provenance — aggregated by reference. | The CLI `context pack`/`--check` aggregates committed facts and runs a fail-closed publish-safety gate; the read-only MCP `agent_context` tool serves it in-memory per request. |
| [`analytics`](./analytics/README.md) | Let a Putnami web application measure its own audience and product usage without shipping visitor data to a third party. | The browser→own-server beacon: the batch and event shapes, the closed enums and bounds, the 18-code error vocabulary, and the shared fixture corpora (valid, one invalid batch per code, a golden batch, bots, user agents, referrers). | Strict-parse with classified decode failures, validate every bound and grammar the TypeScript sanitizer mirrors, and prove the corpus exhausts the closed vocabulary so no reject branch is shared only in prose. |
| [`support`](./support/README.md) | Replace ambiguous public lifecycle wording with one reviewed support-status authority. | The workspace-root `putnami.support.json` catalog with closed subject, status, and parity vocabularies. | Strict-parse shared fixtures and keep the root catalog canonical through the protocol module's conformance gate. |
| [`doccov`](./doccov/README.md) | Make a wire field's meaning checkable, so a protocol cannot ship a field nobody can explain from the types and schemas alone. | No wire shape of its own: a scanner over the sibling packages' exported JSON struct fields and schema descriptions, plus the coverage bar, the shrink-only allowlist, and the ratchet. | Parse sibling sources as text (never importing them), count documented against undocumented wire fields, and fail the gate over the 10% bar, on a vacuous scan, or when an allowlisted package has already caught up. |

## Why these protocols exist

Putnami relies on automation-heavy workflows: CLI commands, extensions, templates, tests, and future platform services all need to agree on the same shapes.

These protocol packages exist so that:

- configuration is **reviewable** in JSON instead of hidden in imperative code,
- automation is **deterministic** because loaders and validators share one contract,
- tooling is **polyglot-friendly** because the boundary is explicit and testable, and
- failures are **actionable** because diagnostics and runtime events are structured.

## Protocol lifecycle checklist

A protocol package (new or changed) meets the bar when it has:

1. **An index entry** — a row in the table above and in the at-a-glance table.
2. **A JSON schema** under `schemas/` for every wire shape.
3. **A fixture corpus** under `fixtures/` with `valid/` and `invalid/` cases — this is the cross-language test surface.
4. **Strict parsing + a conformance test** that runs the corpus through the parser and validator.
5. **At least one real consumer** wired through the package — or an explicit *defined, not yet adopted* marker in its README. A protocol without consumers is a spec, not a contract.
6. **A versioning guard** when the contract is versioned: pin `ProtocolVersion` in a conformance test and, for committed artifacts, enforce a version acceptance window the way `infra/version_test.go` does. State the window — what is read, what migrates, what is rejected on purpose, and the remedy — as a row of the [compatibility budget](../tooling/cli/doc/21-compatibility-and-migration.md), and prove it against **prior-release** artifacts recovered from git history rather than regenerated with the current writer ([ADR 0010](../tooling/cli/doc/adr/0010-compatibility-budget.md)).
7. **Cross-language equivalence fixtures** when more than one language implements it (see `config` hashing, `migration` bundle digests, `infra` manifests).

Pre-public aliases and compatibility readers do not qualify as protocols by
default. A new or retained compatibility seam must have a real current
consumer, a named owning package, and a concrete removal trigger in the
[compatibility budget](../tooling/cli/doc/21-compatibility-and-migration.md).
Negative fixtures that prove an old version or spelling is rejected do not
count as consumers.

## How to use this directory

1. Start with this folder when you need to understand a contract boundary.
2. Open the protocol-specific README for the why / what / how of that package.
3. Use the Go types and strict parsing helpers as the source of truth when wiring new tooling.
4. Run the package tests when changing a protocol so drift is caught immediately.
