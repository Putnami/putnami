# ADR 0034 — A declared output polices its own drift

- **Status**: accepted
- **Scope**: `tooling/cli/internal/jobs` (declared capture and restore),
  `tooling/cli/internal/engine`

## Context

The question "are the committed generated bytes what the current inputs
generate" has one moment at which it can be answered: immediately before the
generator writes. Anything that runs later in the session, such as a verifier
contributed to `validate`, reads a tree the generator, or a cache restore of its
entry, has already rewritten. It compares the session's output with itself and
reports a verdict it did not earn.

The generator task already declares the output it writes (`declares.outputs`).
The engine already captures that output after a run and swaps it in on a hit.
Both write paths belong to the scheduler, so the scheduler judges drift.

## Decision

1. **The scheduler judges drift per declared output, on both write paths.** A
   declared output carrying `drift` (`protocols/extension` ADR 0004) is
   snapshotted, one digest per file, immediately before the task writes it:
   in `prepareTask` before the preBuild hook and the subprocess, and in
   `restoreDeclaredCacheHit` before `materializeDeclaredOutputs` swaps the
   recorded tree in. After the write the same path is walked again. A
   difference is one typed diagnostic, `generated-output-drift`. Under `fail`
   the task fails with that code; its outputs stay written or restored.
2. **The reference for a `pathFrom` output is the project tree.** The path is
   unknown before the run, so the pre-write walk digests the output's root
   (validation admits the project root only) and the resolved path is looked
   up in it afterwards. Both walks skip dot-directories, the project-walk
   exclusions (`dist`, `node_modules`, `vendor`), the output's `excludes` and
   its `preserves` (`protocols/extension` ADR 0005), so both sides see one set.
   The root walk runs only for a task that executes. A hit knows its recorded
   path and snapshots exactly that.
3. **Nothing about drift reaches the cache.** The reference is not a key input
   (`TestDriftReferenceIsNeverACacheKeyInput`). The verdict is applied after
   `finalizeExecutedJob` publishes the task-owned entry, so the successful
   entry stands and the diagnostic never travels in it. `recordableFailure`
   refuses the code, so the failure cache ([ADR 0030](0030-a-failed-task-is-cached-until-its-inputs-change.md))
   never records a verdict that depends on the worktree. The next run hits the
   entry and judges its own worktree.
4. **Three rules keep the two paths at one verdict.**
   - An entry recorded EMPTY is judged against an empty tree. Committed bytes
     found at the path are stale, as the same generator run cold reports. A
     restore of an empty output leaves the path alone, so the diagnostic's
     remedy on that path is a deletion, and it says so.
   - A `pathFrom` output that resolves under a directory the root walk skips
     has no reference on the executed path, so the restore path declines it
     too, with a Warn log and no verdict.
   - A later writer of a policed directory in the same session is judged
     against the earlier writer's bytes. Two emitters that disagree on one byte
     fail the later one on a clean tree: two tools claim one output. A
     coalesced or remote restore is judged like a local hit. Only a plan-level
     follower's failure is left to its leader's row.
5. **No pre-session capture stage exists.** The engine takes no copy of
   generated artifacts before planning ends, and no task receives one. A
   whole-workspace guard (`@putnami/clientgen` `validate`) keeps only what no
   generator task can judge (handwritten transports, inventories, coverage,
   forged markers) and reads committed inputs.

## Consequences

- Five outputs declare `fail`: `@putnami/go` `build-describe.client`,
  `@putnami/typescript` `build-generate.client` and `build-generate.openapi`,
  and `@putnami/clientgen` `clientgen-go.client` and `clientgen-ts.client`.
- The policy must sit on the FIRST writer of a path in a session, or that
  writer erases the evidence first. For a Go provider, `build~describe`
  rewrites `clients/go` before `clientgen~generate-go` does.
- `drift` is part of the task-contract digest: adopting it costs one cold miss.
- A developer who changes a provider API sees one red build whose diagnostic
  names the regenerated files; the next run is green. On CI the same change
  fails from the restore path of the entry that regenerated the files.
- A project a workspace excludes from `--impacted` (a `disable.tags` rule) is
  judged only when it is selected explicitly.
- A directory output that holds hand-authored files beside the generated ones,
  other than its `preserves`, is captured whole. A hit restores the producing
  run's copy of those files, and drift reports it. The fix is a declaration
  that names only the generated closure.

## Alternatives rejected

- **A pre-session byte copy handed to a late verifier.** It costs a copy per
  run plus a nested session and a full render to compare against (about 10 s
  at idle). The writer runs at the right time by construction.
- **A `git` tree object of the worktree.** It excludes ignored paths (some
  generated clients are ignored) and fails outside a git checkout.
- **Require a literal `path` for `drift`.** The client directory is the
  project's configuration, not the extension's.
- **Judge drift in the extension.** Four generators would need four
  comparisons, and none sees the restore path: a cache hit runs no extension
  code.
