# ADR 0121 — An unchanged run writes no file in the work tree

- **Status**: accepted
- **Date**: 2026-11-27
- **Scope**: `@putnami/cli` (`internal/jobs/scheduler`: the build stamp;
  `internal/store`: the held restore), `@putnami/typescript` and
  `@putnami/go` (the generate manifest)

## Context

A run of this repository with nothing changed
(`lint,test,build,validate --all`, 2,194 cache hits) still wrote 1,581 files,
43 MB, all under `.gen`, in 161 `.gen` trees. Each write drops
the witnesses of the input record (ADR 0113) at, under and above its path,
and costs restore work on every run. There were three causes.

1. The `build~generate` and `test~generate` tasks of a TypeScript project
   declare the same `.gen` directory output. The generate manifest,
   `.gen/generate-result.json`, recorded the command mode, `build` or
   `test`, so the two cache entries differed in that one field. A restore
   swaps a differing directory output whole (ADR 0108), so each restore
   rewrote the tree the other task left: 153 manifests, and the whole
   `sites/putnami.dev/.gen`, 1,254 files and 42.5 MB, on every run.
2. The first task of a project that executes rewrote `.gen/version.json`
   with the run's `buildTime`, whether or not its identity had moved. Tasks
   that execute on every run, such as `validate~@putnami/sdd~features`,
   rewrote 161 stamps, 879 KB, on every run. A cache hit already kept a
   matching stamp (ADR 0059).
3. A restore leaves a destination that already holds its output untouched
   (ADR 0108), but the check refused two differences the restore does not
   keep anyway. It refused a directory the entry lacks on the way to a kept
   path. The TypeScript generate cedes `.gen/infra/runtime.json`
   to another task, and its entry holds no `.gen/infra`, so its `.gen` was
   never held and was swapped on every run. And it compared the build stamp
   byte for byte: an entry keyed on the tree serves the commits after the
   one that produced it, its stamp names that commit, and the scheduler
   writes the current commit and source bindings over it after every
   restore (ADR 0059), so every run after a commit swapped the tree again. The guard test below
   found both.

## Decision

1. **The generate manifest does not record the command mode.** The mode
   stays in memory, where the generate phase uses it; nothing reads it back
   from the file. The mode changes how strictly a preBuild hook reports
   diagnostics (the i18n catalog check is strict in `build` mode), not the
   files a successful generate writes, so the two tasks now produce one
   tree and one entry content, and a restore of one over the other's tree
   writes nothing.
2. **An executing task re-stamps `version.json` only when its identity
   changes.** `refreshVersionFile` keeps a stamp whose identity fields
   (`name`, `version`, `suffix`, `sha`, `branch`, `isDirty`,
   `capabilityRoot`, `capabilityPackages`) match the run's, as the plan-time
   seed and the post-hit re-stamp already do. A stamp whose identity differs,
   or a missing one, is written with this run's identity and `buildTime`.
3. **What the restore does not keep is not a difference.** The held check
   accepts a directory of the destination that the entry lacks when it
   leads to a kept path, as the swap itself keeps it (`pruneAround`); every
   other file in it is still compared. It compares the project's build
   stamp, the `<project>/.gen/version.json` the scheduler writes again after
   a restore that replaces it, without the fields that re-stamp writes: the
   fields the scheduler owns, `buildTime`, `sha`, `suffix`, `version`,
   `branch`, `isDirty`, `name`, `capabilityRoot` and `capabilityPackages`.
   The capability inventory belongs there too: its source bindings move
   with a project's files while a generate key that does not read them stays
   put, as a test edit showed on this repository. The fields other writers
   merged, such as `contentHash` and `publish`, are still compared, and the
   re-stamp that follows a held restore brings the scheduler's half to the
   run's when it differs.
   A stamp at any other path of an output is compared whole.

## Rejected

- **Stop the two generate tasks from sharing `.gen`.** A per-mode output
  directory changes the paths every compile, bundle and serve reads, and
  doubles the generated bytes on disk, to separate two trees whose content is
  the same.
- **A per-mode manifest file inside `.gen`.** Both files would sit in the
  shared output; each entry would hold one and the restore would still swap
  the tree.

## Consequences

- `buildTime` names the invocation that first stamped the current identity,
  not the last invocation that executed a task of the project. The suffix
  carries a hash of the uncommitted changes, so a source edit moves the
  identity and the next execution stamps a fresh `buildTime`. An edit to an
  untracked file, or any edit in a workspace Git does not manage, does not
  move the identity, so an execution after it keeps the earlier
  `buildTime`. Its readers are informational: the Go
  `platform.VersionFromGenerated` and the TypeScript platform protocol
  answer it on `/version`, and the TypeScript `getBuildInfo()` hands it to
  application code. No cache key over a plain file pattern holds it
  (`versionStampInvocationFields`), and no deploy or release decision reads
  it.
- A `git:` file-pattern input hashes the stamp's bytes raw, every field
  included. When `.gen` is not ignored, the forced re-stamp moved such a key
  on the run after any run that executed a task; it now moves only when the
  identity does, after a commit or a branch switch.
- `contentHash`, which the TypeScript generator merges into the stamp and a
  running app reads to namespace its disk cache, is untouched: the scheduler
  never wrote it.
- The orchestration counts tests hold the rule: a run of each settling
  extension fixture's unchanged workspace writes no file outside `.git` and
  `.putnami`, by inode, size and modification time, and neither does the
  second run after a commit that changes no file.
- The Go generate manifest drops the mode for the same reason as the
  TypeScript one: its build and serve or run generates share `.gen`.
